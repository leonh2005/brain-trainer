fast-jev-compaction — 機制解說（但你不該用）
更正說明（2026-09-26）：本報告原先把它列為第一順位、標為「最痛點」。但查證後發現 你早已自建同機制的 proxy（~/CCProject/jev-compaction/，port 8788），而且更好：有去識別化層（此套件無，原文直接送出）、插點是每個 request 都先剪一遍（此套件只在 compaction 那一刻動作）、涵蓋整條 ccr 鏈路。已於 2026-09-26 正式啟用。

環境可行性仍實測通過（Claude Code 2.1.283 ≥ 需求 2.1.274、plugin validate 通過、live demo 省 87.1% 字元、258ms），結論是不採用 —— 重複造輪子。

以下機制說明仍值得看，可用來對照你自己的實作：傳統 compaction 是叫 LLM 把舊對話「總結」，但摘要有損：一個檔案路徑、精確錯誤訊息、某個約束條件，可能在後面還需要時就消失了。這個專案的做法是 只刪除、不改寫任何一個字。

  1. 每個 tool_use 與 tool_result 用 tool_use_id 配對；第一則訊息與最新 N 則釘住不動。
  2. 送給 Jev 的是整段對話（工具結果換成短註記如 ok, 4213 chars (omitted)），不摘要任何東西。
  3. 對每個未釘住的呼叫問 Jev 兩個是非題：這個呼叫還值得留嗎？這個結果還需要逐字保留嗎？
  4. 三種結局：結果分數夠 → 全留；否則呼叫分數夠 → 留呼叫但截斷結果；再否則 → 呼叫與結果一起刪。
  5. 使用者與助理的文字永遠逐字保留、維持順序。狀態塞不進 maxStateTokens（預設 25k）時才分階段壓縮。

值得借鏡的一點：它釘住最新 N 則訊息（預設 6）與第一則。你的 proxy 是掃「舊 tool 輸出」，可以對照檢查有沒有等價的保護。

hermes-jev-skills — 10 個 SKILL.md，純檔案

不只 Hermes，Claude Code 也能吃。把 agent 一天當中的「小決定」全交給 Jev：

檢索結果哪些值得打開、證據是否足夠~1.9s/輪
記憶：哪些段落值得讀、哪些含隱藏指令（注入防護，Jev 掛掉時仍本地跑）60 段/請求

訊息急迫度與分類~0.4s，$0.00006
收件匣分派~$0.00002/封
下一個 GUI／瀏覽器動作~0.4–0.5s/步

最關鍵：它把 shadow mode 當一等公民 —— jev routing shadow「決定並記錄，但不切換任何東西」。README 原話："Start in shadow mode. It is the honest way to see what Jev would do before it does anything." 這正是你現在跑的模式。

它還有一個誠實的發現：用 Jev 的 keep／summarize／drop 摘要寫出的 handoff，recall 反而比直接給原始逐字稿低（58.7% vs 75%），所以最後出貨的是完整對話。會實測後否決自己想法的專案，通常比較可信。
